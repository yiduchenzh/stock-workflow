# 全自动交易 · 大道至简重构方案（3 引擎）

> 2026-09-27 起草 · 依据：当日全景审计（`docs/_panorama_20260927/`）＋ 3 引擎实时实测
> 前提（我的理解，若反了请一句话纠正）：**三套战法的内在交易逻辑不动**（昨收战法 / 昨收15分K / 缠论各自怎么买卖，不改），
> 只对 **"战法之外的重复基础设施"** 做减法——数据、选股、盯盘、执行、风控、记账、页面。

**代码同源证据**：①∩③ 同名函数 **27 个**（`_tick/_loop/_sell/_open_buy/_daily_rows/_quotes_map/_refresh_positions/_limit_pct_of/_is_trading_day/...`），Jaccard **0.55** → ①③ 是复制粘贴演化的两份副本；② 另起一派（Jaccard 0.05）。

**由此产生的真实缺陷（本次审计已实测）**
1. **战绩不可比**：①几乎不扣费、②扣费（0.35% 口径）、③口径不明 → 三个账户的"已实现盈亏"不能横向比。
2. **无组合级风控**：三引擎各自 `market_guard`，但**合计敞口/合计日亏无人管**；今天三引擎分别持 5/3/5 只、合计 13 只、净 -3.15%（②）/ -7.95%（①含浮亏）。
3. **同一份行情拉三遍**，且 ②连共享库都不用 → 数据源故障时三引擎表现不一致，排查要查三条链。
4. **前端三页各自为战**：无一处能一屏看全 3 引擎合并持仓与总敞口（本次审计 P1）。
5. ①∩③ 同源分裂：**同一个 bug 要修两遍**（今天的 `trade_stats` 缺失就是①的；③修不修没人知道）。

## 二、结论先说：不合并战法，合并基础设施；但**战法层要各自做减法**（三种病不同）

**答案分两层**（这是对"3 个合并 or 各自简化"的直接回答）：

**第一层（基础设施）→ 合并**：三套数据链/选股/盯盘/记账/风控 = 五个器官各写三遍（实测 ①∩③ 27 个同名函数），必须收成一套。
**第二层（战法层）→ 各自简化**：三个引擎得的是**三种不同的病**，药不能乱吃（见 §1.5 基线）。

一句话结构：

```
                    ┌─────────── 共享内核（唯一实现）───────────┐
  数据门面 ── 候选池 ── 盯盘调度 ── 执行/记账 ── 风控闸门 ── 组合视图
                    └──────────────┬───────────────────────┘
              ┌────────────────────┼────────────────────┐
       战法①昨收战法         战法②昨收15分K          战法③缠论
   病=坏价吃利润         病=退出单一化           病=碎单高频磨损
   药=坏价护栏(上提内核)  药=退出分层(止盈/移动)   药=最小成交额+减仓频次上限
```

### 1.5 同口径基线（Phase 0 已执行 · `hunter-v2/scripts/engine_parity.py`）

改造前**三个引擎的战绩本来没法比**（①③无费用模型、②有）。统一到 ② 的费率口径（买 0.026% / 卖 0.076% 含印花）后：

| 引擎 | 平仓回合 | 胜 | 负 | 胜率 | 毛已实现 | 净已实现 | 费用拖累 | 净值(成本计) | 对初始 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| ①昨收战法 | 4 | 0 | 4 | 0% | -10,782 | **-10,808.63** | 26.63 | 89,084.52 | **-10.92%** |
| ②昨收15分K | 4 | 1 | 3 | 25% | +1,073 | **+913.44** | 159.56 | 100,890.29 | **+0.89%** |
| ③缠论 | **156** | 27 | 129 | **17.3%** | -2,212 | **-2,698.27** | 486.27 | 96,271.21 | **-3.73%** |
| 合计 | 164 | 28 | 136 | | | **-12,593.46** | | 286,246.02 | -4.58% |

**三种病的病理（逐笔证据）**
- **①=坏价吃利润**：4 个回合里单笔 `300189 神农种业 均价7.63 → 成交0.07` 就亏 **-9,830.65**，占 ① 全部亏损的 **91%**。剔除后 ① 实际约 **-1%**。→ **药：坏价护栏上提到共享内核（一处实现，三处受益）**。
- **②=退出单一化**：4/4 笔离场原因**完全相同**（"放量有效跌破昨收"），没有一笔走止盈/移动止盈；唯一盈利 +8.92% 贡献全部正收益。→ **药：退出分层**（止盈/移动止盈/止损/破位四类，各管一段），并把 +9% 那种"让利润奔跑"固化。
- **③=碎单高频磨损**：`62 买 / 156 卖`，其中 **141 笔是"顶分型减仓级"**；卖出金额中位仅 **2,352 元**（61% 的卖出 < 3000 元）；**74/156 笔（47%）|pnl| < 0.2%**（在成本附近反复进出）；双边费率 0.102% ≈ 单笔波动量级 → **手续费在蚕食本金**。→ **药：最小成交额门槛（如 <1 万不做）+ 同票减仓频次上限**（与已验证的 `max_t0_rounds` A/B 同源）。

> 这条基线是**每一步简化的验收标尺**：改造后重跑 `engine_parity.py`，三引擎的回合数/净额变化必须能解释（预期：③ 回合数大降、费用拖累大降；① 剔除坏价后转正）。
**为什么不是"只合成一个引擎"**：三套战法的**入场/离场条件、时间尺度、持仓周期完全不同**（①开盘确认买/尾盘池；②15分K 破位离场；③分型/中枢级别/减仓分级），
且三者**病根不同**（坏价 / 退出单一 / 碎单高频）。硬合成一个类 = 在一个 3000 行文件里塞三套状态机 + 三套药方 → 那是"加法"。
**为什么不是"只各自简化"（不合并内核）**：三份重复会继续分叉（①③同源已经分叉成 27 个同名函数），
每个 bug 修三遍、三处口径永远对不齐（今天已经实测：①③无费用模型、②有）——这是"越走越散"。
**所以：器官合并（内核），药方分开（战法层）。**

**判据（大道至简的真正含义）**：**"一处实现、三处复用"**——凡是"三套里逻辑应该相同的"（T+1、涨跌停可成交、费用、成交回执、持仓估值、交易日闸）必须收敛成 1 份；
凡是"三套里逻辑天生不同"的（买点/卖点/池子/离场）保持 3 份。**减的是重复，不是策略。**

## 三、五个"三套变一套"的减法（按收益/风险排序）

### 减 1：执行与记账内核（最痛、最先做）
- 现状：T+1 锁定/涨跌停/**费用**/成交回执/持仓估值 在 3 处各写一遍；①③**没有费用模型**。
- 目标：`backend/exec_kernel.py`（新）唯一实现：`can_buy/can_sell(涨跌停·T+1·停牌)`、`fees(买卖·印花税)`、`fill()`、`mark_to_market()`。
- 收益：**三引擎战绩变为同口径可比**；`trade_stats` 这类"类侧契约"统一；①的 `0.07 元坏价成交`类问题只需在一处加护栏。
- 验收：同一天同一笔成交，三引擎记账金额差 = 0（对拍脚本）。

### 减 2：数据门面（去掉 ② 的私有取数路径）
- 现状：3 条链；②只读 `KlineCache`，①③直连 mootdx/腾讯/东财。
- 目标：`backend/market_gateway.py`（新）——`quotes()`（stock-sdk 快照）＋`kline(日/5分/15分)`（共享库 `D:\MarketData\market.db` 或 hunter 库）＋**降级链集中一处**；三引擎只调门面。
- 收益：拉取次数 3→1（同样 5568 只行情，每天少拉两遍）；数据源坏了一次性修；②能拿到共享库覆盖。
- 验收：门面命中缓存时单次调用 < 200ms；三引擎同票同日 K 线字节级一致（对拍）。

### 减 3：候选池（选股从"扫 3 遍"变"扫 1 遍，三战法各自过滤"）
- 现状：①`_scan_pool`、②`universe`(5545→103→5)、③`chanlun_scan` 各自全市场扫描。
- 目标：`backend/pool_service.py`（新）：收盘后（15:05）**一次全市场扫描**产出统一候选池（含代码/名称/涨跌幅/量比/距20日高/板块/成交额/换手…），落 `data/pool_YYYYMMDD.json`；三战法用**各自过滤器**从池中取子集（①强势池护栏、②trend_sector_leader+分位、③缠论结构判定）。
- 收益：全市场扫描 3 遍 → 1 遍（这是每天最贵的 I/O）；三战法共享同一份"当日事实"，避免"同一天三个引擎对同一只票给出互相矛盾的池子"。
- 验收：候选池构建 ≤ 60s（现 ② 选择 scanned 5545）；三战法候选集与改造前**逐个对照**（差异必须能解释）。

### 减 4：盯盘调度器（3 个 sleep 循环 → 1 个分频调度）
- 现状：三个 daemon 线程各自 sleep、各自时段窗；**同一秒可能三个线程同时打行情接口**。
- 目标：`backend/watch_scheduler.py`（新）：三层分频（市场层 60s / 板块层 60s / 个股层 15s）＋三战法注册为 `on_tick(ctx)` 处理器；行情在同一 tick 内共享。
- 收益：接口压力 ↓、时序可控（今天审计发现"三引擎 last_tick 停滞"是误报，但**时序不可视**是真问题）；盘后自动收工。
- 验收：一个交易日内三战法 `on_tick` 调用次数符合分频预期；行情接口日均调用量下降 ≥50%（对比改造前日志）。

### 减 5：风控闸门（3 个独立 → 1 个，且升级到组合级）
- 现状：三个 `market_guard` 各判各的；**无组合级敞口/日亏熔断**。
- 目标：`backend/risk_gate.py`（新）：①**大盘环境门控**（唯一被 75 条实证证明有效的组合级改进：跌破 MA20 减半/停新开）②组合级总敞口上限 ③组合级日亏/连亏熔断（复用 stock-workflow 已成熟的 budget/Fuse/breaker 三闸经验）④单票集中度。
- 收益：从"三个各管自己"升到"一个账户视角管三个战法"——这才是"活得更久"。
- 验收：注入一次"大盘跌 1.5% 的模拟 tick"，三战法都应被拦新开仓；组合敞口数字与手工汇总一致。

### （减 6：页面）3 页 → 1 页 3 Tab + 1 个组合总览
- 现状：`/auto-trade`、`/prevclose15-auto`、`/chan-trade` 三页，顶部统计各写一套；无合并视图。
- 目标：**一个"全自动交易"入口**：顶部=组合总览（净值/敞口/日亏/胜率口径统一），下面 3 个战法 Tab（复用现有页面主体，逐页迁移）；再补"风控页"（本次审计 P1：`trade/risk-check` 有数据无页面）。
- 收益：交易员要的是"做什么/输得起多少/错了怎么办"，一屏能看到三战法合力。

## 四、三条路线对比（决策表）

| 维度 | A 合并成 1 个引擎 | **B 3 战法保留 + 共享内核（推荐）** | C 各自简化、保持独立 |
|---|---|---|---|
| 战法逻辑改动 | 必须重写（高） | **0（只搬基础设施）** | 0 |
| 代码量变化 | 3315 → ~1500 行（大重写） | 3315 → 内核 ~600 行 + 3 插件各 ≤300 行 | 3315 → ~2400（各减 30%） |
| 战绩可比 | 好 | **好（减1 就达成）** | 仍不可比 |
| 组合级风控 | 好 | **好** | 做不到（还是三个各管自己） |
| 风险 | 高（回归面大、一次性切换） | **低（逐层抽，每步可回滚、可 A/B）** | 低 |
| 收敛速度 | 慢（要先啃 3000 行） | **快（每层独立交付）** | 不收敛（继续分叉） |
| 适合 | 战法本身重复度高时 | **战法不同、基础设施重复（当前实况）** | 只想止血时 |

**推荐 B，并按"痛点 × 低风险"排序落地：减 1（记账）→ 减 2（数据）→ 减 3（候选池）→ 减 4（调度）→ 减 5（风控）→ 减 6（页面）。**

## 五、分阶段执行（每步都带验收，均可回滚）

### Phase 0（✅ 已完成，零风险）
- 已交付 `hunter-v2/scripts/engine_parity.py`：把 3 引擎状态文件读成统一口径（FIFO 平仓回合 + 统一费率），输出"改造前基线表"。
- 产出：`docs/_panorama_20260927/engine_parity_baseline.json` + 上文 §1.5 基线表。
- 为什么先做：**没有基线就无法证明简化是正确的**（改造后重跑同一脚本对拍）。

### Phase 0.5（P0，半天）：③ 的"碎单门控"（预期收益最大、改动最小）
- 只动"下单闸"，不动买卖判断：最小成交额门槛（<1 万不执行）+ 同票减仓频次上限（如 N 日内 1 次）+ 减仓比例下限（避免 100 股碎单）。
- 依据：③ 156 卖出中 141 笔是"减仓级"、中位金额 2,352 元、47% 在成本附近进出 → 费用≈波动。
- 验收：同等信号下，③ 的回合数与费用拖累显著下降（目标：回合 < 40，费用拖累 < 150），且**累计净额不低于改造前**。

### Phase 1（P0，半天）：减 1 执行/记账内核
- 新 `backend/exec_kernel.py`；三引擎改为调用它（**先"双跑对拍"再切换**：同一笔成交，新旧记账结果必须一致，误差>0 就回退）。
- 验收：parity 脚本显示三引擎费用口径一致；①的历史 `0.07 坏价`在护栏下会被拦。

### Phase 2（P0，1 天）：减 2 数据门面
- 新 `backend/market_gateway.py`，三引擎取数改走它（含降级链集中）。
- 验收：三引擎同票同日 K 线一致；行情拉取次数降至 1/3；`/api/v1/health` 与三引擎状态均正常。

### Phase 3（P1，1–2 天）：减 3 候选池 + 减 5 风控闸门
- `pool_service.py` 15:05 一次扫描；`risk_gate.py` 组合级闸（大盘门控 + 总敞口 + 日亏熔断）。
- 验收：三战法候选集与改造前逐票对照（差异有解释）；模拟大盘跌 1.5% → 三战法都被拦。

### Phase 4（P1，1 天）：减 4 盯盘调度器
- `watch_scheduler.py` 三层分频；三战法注册 `on_tick`。
- 验收：分频计数符合预期；行情接口调用量下降 ≥50%。

### Phase 5（P2，1–2 天）：减 6 页面
- 1 个"全自动交易"入口（组合总览 + 3 战法 Tab）+ 风控页（挂已有 `trade/risk-check`）。
- 验收：用户旅程——"一屏看清 3 战法合力 + 今天该不该开新仓"。

### 不做什么（同样重要）
- ❌ 不动三套战法的买卖规则/参数（本次"按计划"已证明：改参数前必须 A/B）
- ❌ 不做"大爆炸"式重写，不引入新框架（FastAPI/React 保持）
- ❌ 不为了让代码好看而删功能页面（今天已删的 xlnn 是"用户决定"，不是"重构顺手"）
- ❌ 不合并账户资金（三账户独立是**有意设计**：对照实验。共享的是基础设施，不是钱）

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 抽层时改变行为 → 战绩漂移 | 每层"双跑对拍 + 基线表"；parity 脚本进 CI 手动跑 |
| ②不依赖共享库，抽数据门面时它最脆弱 | 先给 ② 做"门面只读旁路"（不改它的计算），对拍通过再切主路 |
| 三引擎同源复制（①③）→ 修一处漏一处 | 减 1 落地后，①③ 的 `_sell/_limit_pct_of/_daily_rows` 直接改为调用内核，删除副本 |
| 组合级风控上线后开仓变少（可能误杀） | 沿用已验证的"先量测通过率再调闸"（风控闸连环误杀排查方法论） |
| 当天业绩受冲击 | 只在**非交易时段**切换（周末/盘后），每步一个 commit，可一键回滚 |

## 七、一句话总结

**三套战法留着，五套重复的基础设施合成一套——把"三头马拉一辆车"改成"一台发动机 + 三种变速箱"。
简化的是"每天扫三遍全市场、三个循环各打一次行情、三处各写一遍费用、三个风控各看自己"，不是策略本身。**
